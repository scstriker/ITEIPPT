# 04 - Risks And Next Actions

> 目标：先控风险，再迭代功能，避免反复返工。

## A. 当前风险

### 1) 编码污染仍在（高）
- 现象：`UploadPanel`、`functions` 等文件存在中文乱码字面量。
- 风险：用户可见文案异常，后续改动时易引入误判或回归。

### 2) 工作区高脏状态（高）
- 现象：大量 `A/AM/??` 文件混合。
- 风险：迁移或提测时容易把实验性改动一并带入。

### 3) 双后端实现漂移（中）
- 本地代理：`src/services/apiProxyServer.ts`
- 云函数：`functions/src/index.ts`
- 风险：本地通过但云端行为不一致。

### 4) 视觉回归缺少自动化（中）
- 二级标题自适应、正文高亮语义等主要靠人工验收。
- 风险：模板调整后难以及时发现排版退化。

### 5) 前端打包体积偏大（中）
- `vite build` 仍提示 chunk 过大警告。
- 风险：首屏加载与维护成本上升。

## B. 建议接手顺序
1. 冻结当前可运行快照（新分支 + 最小提交）。
2. 先做“中文文案编码清理”专门批次，单独提交。
3. 做一次“代理 vs functions”协议一致性对齐。
4. 增补最小自动化验证（至少 API 契约 + 高亮算法单测）。
5. 再进入新需求开发。

## C. 下一迭代建议（短周期）
- N1：编码清理专项（`UploadPanel`、`apiProxyServer`、`functions` 常量文本）。
- N2：补 `/api/generate-content` 的高亮语义回归测试样例。
- N3：为内容页标题自适应增加极端长标题可视化快照测试。
- N4：整理提交边界，拆分“功能改动”与“文案/样式修复”。
- N5：评估前端拆包策略，降低单包体积警告。

## D. 迁移后首日验收基线
- [ ] 上传 -> 规划 -> 配图 -> 审计 -> 导出链路可完成。
- [ ] `src` 的 `lint/build/proxy:smoke` 全绿。
- [ ] `functions` 的 `npm run build` 通过。
- [ ] Step2/Step3 关键交互与对齐满足当前 UI 规范。
- [ ] 内容页标题与正文高亮逻辑符合“自适应 + 语义优先”预期。
